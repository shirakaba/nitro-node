# Nitro v1 on Node.js (macOS proof of concept)

Working: a native `.node` addon wraps Node's existing JavaScript environment with Microsoft's **node-api-jsi**, installs Nitro v1's unmodified C++ core, and exposes a small C++ `HelloWorld` HybridObject. JavaScript runs in Node's V8 engine. There is no Hermes runtime or React Native application involved.

## Run

Requirements: macOS, Node.js, pnpm, CMake, and Xcode Command Line Tools (Apple Clang with C++20 support).

From the repository root:

```sh
pnpm install
pnpm --filter nitro-node build
pnpm --filter nitro-node hello
pnpm --filter nitro-node test
```

The example prints:

```text
Hello, macOS! From JSI on Node.js.
Hello, macOS! From Nitro v1 on Node.js.
[HybridObject HelloWorld]
```

The build uses locally installed Node-API headers, first looking next to the running Node executable and then in Homebrew's include directories. If needed, set `NODE_INCLUDE_DIR` to a directory containing `node_api.h`. After installing dependencies, building requires no further downloads. The output is `packages/nitro-node/build/nitro_node.node`.

## Use

```js
import { jsiHello, NitroModulesProxy } from "./packages/nitro-node/index.js";

console.log(jsiHello("World"));

const HelloWorld = NitroModulesProxy.getHybridClass("HelloWorld");
const hello = new HelloWorld();
console.log(hello.greet("World"));
```

The ESM entry point loads the native addon with `process.dlopen()` and exposes named exports. Both packages declare `"type": "module"`, so JavaScript files use `.js` extensions. Workers use dynamic `import()` to load the entry point in their own environments.

`jsiHello` is a plain JSI HostFunction. `HelloWorld` uses Nitro's actual `HybridObject`, `HybridClass`, argument conversion, constructor/prototype creation, and native-state storage. Its class descriptor is handwritten for this small example, rather than generated by Nitrogen. Both entry points are installed into the real Node global object and also exported by the addon.

The addon uses `nitro::install(runtime)` and compiles every source file in the installed package's `cpp/core/src` and `apple/core/src`, without editing Nitro. The Apple core provides pthread/dispatch thread utilities and logging. It does not import Nitro's React Native JavaScript entry point, which still uses `TurboModuleRegistry` for initialization. React Native's installed package supplies the JSI headers and `jsi.cpp`; React Native framework code, TurboModules, and Apple UI integrations are not linked. The linker permits only the addon's explicit Node-API imports to remain unresolved, so missing Nitro/JSI dependencies fail the build.

## Compatibility findings

- **Apple Clang works.** MSVC and a Windows VM are unnecessary for this example. Upstream's top-level CMake project builds Windows-oriented tests and its POSIX dynamic loader is unfinished. This repository supplies an addon build and implements the missing loader with `dlopen`/`dlsym`.
- **The JSI version gap did not block this example.** node-api-jsi is pinned to commit `4b8a4a59c4e1b7b988b809dedffd89a7662aa785` and supports branches through `JSI_VERSION=21`. Its runtime implementation compiled against the installed **React Native 0.88.0** JSI headers without source changes. Newer operations used by Nitro, such as runtime data storage and object creation with a prototype, have defaults in the current JSI `Runtime` implementation.
- **Node-API stability does not make arbitrary JSI C++ binaries compatible.** Nitro, node-api-jsi, and `jsi.cpp` are compiled together against the same JSI headers. `JSI_VERSION=21` selects the upstream adapter's implemented feature branches; it does not downgrade the installed headers or make different JSI vtables interchangeable. This result establishes source compatibility for this build and the exercised behavior, not blanket support for every future JSI feature.
- **“Decoupled” refers to the core and host integration.** The installed v1 package separates its C++ core from the React Native adapter. The latter still uses a TurboModule to obtain a runtime and call `nitro::install`. Node supplies that runtime through node-api-jsi instead.

Verified on this Apple Silicon Mac with Apple Clang 21.0.0 and Nitro `1.0.0-alpha.nightly.100.g107f6fc66597`. The **same arm64 addon binary**, built using Node 24.14.0 headers, passes all eight integration tests on Node **20.12.2**, **22.19.0**, and **24.14.0**. The tests exercise direct JSI calls, shared bindings across static/dynamic/package ESM imports, Nitro class construction and inheritance, Unicode and embedded NULs, error recovery, disposal, calls after event-loop turns and forced garbage collection, and concurrent Workers with clean exits.

## Scope

This is a synchronous C++ proof of concept. Nitro's async overload needs a Node-aware `Dispatcher`; it is not installed here. Upstream's microtask enqueue fallback returns an error, and its external-memory-pressure implementation is a no-op. Async methods, all JSI APIs, Swift/Objective-C modules, UI components, Intel macOS, and packaged prebuild distribution have not been validated.

The `vendor/node-api-jsi` directory contains only the upstream runtime, API loaders, and Node-API headers needed for this build, with their licenses and a provenance note. See [the upstream project](https://github.com/microsoft/node-api-jsi) and [local changes](packages/nitro-node/vendor/node-api-jsi/README.md).
